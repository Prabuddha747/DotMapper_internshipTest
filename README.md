# Support Intelligence AI

An AI-powered analytics system over a customer support ticket dataset:
natural-language question answering (Groq LLM), deterministic anomaly
detection, a REST API, and a browser UI — built so every numeric answer is
computed from the real data, never generated by the model.

## 1. Overview

**Use case.** A support team lead wants fast answers about ticket volume,
agent performance, SLA breaches, and anomalies — without writing SQL or
opening a spreadsheet. This system lets them type a plain-English question
("Which agent has the lowest average rating?") and get back a real,
computed answer, backed by an evidence trail of exactly which rows produced
it.

**Core design principle.** The LLM is used only for *understanding* the
question — it converts a natural-language question into a structured
intent (an operation + filters, e.g. `{"operation": "average", "field":
"customer_rating", "filters": {"category": "Technical"}}`). It never
computes or writes the numeric answer itself. All arithmetic runs in
pandas, against the real in-memory dataset. This removes numeric
hallucination as a failure mode entirely: a bad LLM call can pick the wrong
operation, but it can never report a wrong number for the right one.

## 2. Architecture

```
support_tickets.csv → ingestion.py → in-memory pandas DataFrame (app.state)
                                            │
                       ┌────────────────────┼────────────────────┐
                       ▼                                          ▼
                 query_engine.py                            anomaly.py
      (count/filter/group/avg/sum/min/max/ratio/equalize)   (IQR + rules)
                       ▲
                       │ structured intent (JSON)
                    llm.py ── Groq API
                       ▲
                       │ NL question
                    main.py (FastAPI) ── static/ (HTML/CSS/JS UI)
```

| Component | Choice | Why |
|---|---|---|
| Backend | FastAPI | REST API with free interactive docs at `/docs` |
| Data store | pandas DataFrame in memory | ~500 rows, single reader/writer, re-ingested on every boot — a database would add a persistence layer with no concurrency problem to solve |
| Analytics | pandas | filtering, grouping, and aggregation without a SQL layer |
| LLM | Groq (`openai/gpt-oss-20b`, configurable) | free tier, low latency, strict JSON-mode output |
| UI | plain HTML/CSS/JS | a stat-card dashboard, a question box, and a results panel — no framework or build step |
| Anomalies | pandas + IQR | deterministic and explainable, no model training |

**Deliberately not used:** a database, vector search / embeddings,
LangChain-style agent frameworks, Docker. The dataset is small and
structured; none of the target questions need semantic retrieval, and
none of the operations need a persistence layer beyond the source CSV.

## 3. Features

- **Ingestion** — loads the CSV once at startup into a validated in-memory
  DataFrame (schema and column-type checks fail fast, with a clear error).
- **Natural-language querying** — count, filter, group-by, average, sum,
  min, max, **ratio** (sum/average of two fields plus their ratio), and
  **equalize** (see §6), each with optional equality, multi-value, and
  numeric-comparison (`>`, `>=`, `<`, `<=`) filters.
- **Anomaly detection** — three independent, explainable rules (overdue
  unresolved tickets, statistical resolution-time outliers, data-quality
  violations).
- **REST API and UI** — both expose the same functionality; the UI is a
  thin client over the same endpoints.
- **Evidence envelope** — every `/api/query` response includes the data
  source, the number of real rows the answer was computed from
  (`rows_used`), and a timestamp, so an answer's provenance is always
  visible.

Requires Python 3.10+.

```bash
git clone https://github.com/Prabuddha747/DotMapper_internshipTest.git
cd DotMapper_internshipTest

python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
```

## 6. Example queries and real outputs

Run live against this dataset (`gpt-oss-20b`, temperature 0):

**"How many tickets are currently open?"**
```
{"operation": "count", "filters": {"status": "Open"}} → "111 ticket(s) match those filters."
```

**"Which agent resolved the most tickets?"**
```
{"operation": "group_count", "group_by": "agent_id", "filters": {"status": "Resolved"}} → "Top agent_id: AGT-09 (37 tickets)."
```

**"What is the average customer rating for Technical category tickets?"**
```
{"operation": "average", "field": "customer_rating", "filters": {"category": "Technical"}} → "The average customer_rating is 3.74 (over 104 tickets)."
```

**"Show me all Critical tickets not resolved within 12 hours."**
```
{"operation": "filter", "filters": {"priority": "Critical", "resolution_time_hrs": {"gt": 12}}} → "3 ticket(s) match, showing 3."
```

**"Are there any anomalies in resolution times?"**
```
{"operation": "anomaly_summary"} → "101 anomalies found: 80 overdue_unresolved, 21 resolution_outlier"
```

**"What is the minimum percentage of tickets that must move between
statuses to make Open, Escalated, and Resolved equal?"**
```
{"operation": "equalize", "group_by": "status"} → "To make status categories equal (166.7 each of 500), 160.33 ticket(s) must move: Resolved gives away 160.33 (49.0%), Open receives 55.67, Escalated receives 104.67"
```

**"What is the total sum of response time and resolution time, and their ratio?"**
```
{"operation": "ratio", "field": "response_time_hrs", "field_b": "resolution_time_hrs", "agg": "sum"} → "sum of response_time_hrs: 1310.3; sum of resolution_time_hrs: 6264.8; ratio response_time_hrs/resolution_time_hrs = 0.2092."
```

## 7. Edge cases handled

These were found and fixed by adversarially testing the running system
with real, messy phrasing — not just the documented sample queries.

| Edge case | Behavior |
|---|---|
| Off-topic question ("who are you?") | Returns a clean JSON error instead of leaking a raw LLM/API error to the caller. |
| Hypothetical / "what-if" question that expects a *new, simulated* distribution (e.g. "if tickets rotated between statuses, what would the new percentages be?") | Returns an honest "can't simulate hypothetical changes" error instead of silently answering with the real, unrelated current data. |
| A "what-if" that is actually well-defined arithmetic on real data (e.g. "what's the minimum % of tickets that must move to make each status equal?") | Answered correctly via the `equalize` operation — swapping which label owns a count doesn't change the arithmetic needed to equalize it, so this is not a simulation and is safe to compute. |
| Compound question needing two fields at once (e.g. "sum of response time and resolution time, and their ratio") | Answered via a dedicated `ratio` operation instead of being wrongly rejected as unsupported — sum/ratio of two real columns is ordinary arithmetic, no different in kind from a single-field `sum`. |
| Model returns inconsistent enum casing (`"critical"` instead of `"Critical"`) | Filter validation matches case-insensitively and substitutes the canonical value. |
| Model references an unknown column or enum value | Dropped and reported back in the response (`dropped_filters`) instead of silently ignored or crashing. |
| Numeric filter needed but schema only supported equality (e.g. "not resolved within 12 hours") | Added `{"gt"/"gte"/"lt"/"lte": n}` comparison filters after live-testing revealed the gap. |
| Comparison against a nullable numeric column (`resolution_time_hrs` is null until resolved) | `NaN` never satisfies a `>`/`<` comparison, so unresolved tickets are correctly excluded rather than matched by accident. |
| Zero rows match a filter | Returns `count: 0` / an empty result set, not an error. |
| Average/sum/min/max over an all-null or empty filtered set | Returns `None` and `matched: 0` rather than `NaN` or a crash. |
| Groq rate limit hit | Distinct, actionable error message ("wait a moment and try again") instead of a generic failure. |
| Groq request fails, times out, or returns malformed JSON | Every failure mode degrades to a clean JSON error; `extract_intent()` never raises. |
| Groq's JSON-mode validator rejects a generation (e.g. the model tried to explain a limitation in prose) | Generic, accurate error message — never claims the question is off-topic, since this also fires for on-topic compound questions the model can't express in one operation. |
| `GROQ_API_KEY` not configured | `/api/query` reports the missing key cleanly; `/health`, `/api/anomalies`, `/api/stats` remain fully usable. |
| Response values containing NaN / pandas Timestamps / numpy scalars | Converted to JSON-safe types before serialization (`None`, ISO strings, native `int`/`float`) — this is verified by dedicated tests, not just assumed. |

## 8. Anomaly detection logic

"Now" is defined as the latest `created_at` in the dataset, not the wall
clock — the data is historical, so a live clock would flag every ticket as
ancient.

- **Rule A — overdue unresolved**: status in (Open, Escalated) AND priority
  in (High, Critical) AND age past creation > 24h.
- **Rule B — resolution-time outlier**: for resolved tickets, flag
  `resolution_time_hrs > Q3 + 1.5 × IQR` (skipped if fewer than 4 resolved
  tickets exist, since quartiles are meaningless below that).
- **Rule C — data quality**: resolved tickets missing required fields, or
  rows with an invalid category/priority/status value — kept for
  robustness against a dirtier dataset even though this CSV is clean.

## 9. Design decisions

- **LLM never computes numbers** — it only selects an operation and
  filters; `query_engine.py` performs every calculation, so the answer
  text is always traceable to a real pandas computation.
- **In-memory pandas, no database** — appropriate at this data size and
  access pattern (single reader, re-ingested on boot); a database adds a
  persistence layer with nothing to persist.
- **No vector database or retrieval-augmented generation** — the dataset
  is small and structured; nothing in the target queries needs semantic
  search over free text.
- **Case-insensitive enum matching** — live testing showed the model
  sometimes returns lowercase enum values even when told the exact casing.
- **Rate-limit handling** — the free-tier rate limit is caught specifically
  and surfaced with an actionable message; the UI also disables the Ask
  button while a request is in flight to avoid burning quota on rapid
  re-clicks.

## 10. Known limitations

- "This week" / "today" resolve against the dataset's latest timestamp,
  not the real-world date — the data itself is historical.
- SLA-style phrasing like "not resolved within N hours" has two valid
  readings (resolved late, vs. still open past the threshold); the model
  picks one interpretation per call rather than returning both.
- No persistence across restarts — the CSV is the single source of truth,
  intentionally re-loaded on every boot.
- No authentication, multi-tenancy, or containerization — out of scope for
  a local, single-evaluator system.
- Groq free-tier model availability differs by account; if the default
  model isn't enabled on a given key, set `GROQ_MODEL` to one that is.
- The underlying model is not perfectly deterministic even at
  `temperature=0` on borderline-phrased questions — the same question can
  occasionally route to a different (still valid) operation across calls.

## 11. What could be improved with more time

- Parse an explicit N-hour threshold out of the question text for
  SLA-style queries, instead of relying on a fixed 24-hour anomaly rule or
  a single manually-specified comparison filter.
- A free-text search operation over `issue_summary` (substring or
  keyword match; no embeddings needed at this data size) for
  "tickets mentioning X" style questions.
- A lightweight per-session conversation history, so a follow-up question
  ("...and by agent?") can inherit filters from the previous one instead of
  needing to be fully self-contained.
- Containerize with a single `Dockerfile`/`docker compose up`, if the
  system needs to run somewhere other than a local evaluator machine.
- Expand `equalize`-style closed-form operations to other useful
  what-if-shaped-but-actually-deterministic questions, if real usage shows
  more of them.

98 tests total (91 mocked + 7 live), 100% statement coverage on `app/`:
ingestion/schema validation, every query operation (including comparison
filters, JSON-serialization safety, and the `ratio`/`equalize` operations),
all anomaly rules including boundary and degenerate cases, LLM intent
validation against a mocked Groq client (malformed JSON, rate limits,
case-insensitive enums, dropped filters, missing key), and FastAPI endpoint
behavior including graceful degradation and evidence-envelope checks. The
live tests hit the real Groq API to catch semantic failures a mock can't:
off-topic questions, hypothetical/what-if questions, the compound
sum-and-ratio question, and known-answer questions verified against the
real dataset.
